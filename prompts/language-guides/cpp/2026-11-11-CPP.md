# C++ engineering guide

These rules shape the C++ you write or change; they are not a checklist of things to add. What the request specifies wins, then the project's conventions: its C++ standard, error style (exceptions, `-fno-exceptions`, status types), build system and toolchain. Where nothing is set, write C++23, and confirm that the target toolchain has a newer feature (its `__cpp_lib_*` macro in `<version>`, or `__cpp_*` for a language feature) before using it: `std::move_only_function`, `std::flat_map`, `<mdspan>`, C++26 features and `import std` (which also needs build-system support) are missing from many shipped toolchains. Don't add build or lint configuration, dependencies, wrapper types, targets, helper modules or hardening that the task doesn't need, and don't modernize or rewrite working code to match this guide: report what you noticed instead. A bullet that starts with a context (`CMake:`, `POSIX:`) applies only there.

## Targets and build

- CMake: dependencies point one way, and a part some consumers don't need (HTTP client, database driver, GUI) is its own target, so a small executable doesn't link it. Link `PRIVATE` unless your public headers include the dependency's. When you split a target, keep the old name as an `INTERFACE` target over the parts so targets that link it build unchanged. Don't split a single-target project unasked.
- CMake: a build stamp (git hash) goes into one generated source file in a tiny target of its own, rewritten by a build-time command only when the value changes; as a compile definition it is either stale until the next configure or, if refreshed on each build, recompiles the whole library on every commit.

## Types and zero-cost abstractions

- Ids and constrained values that cross an API, wire or storage boundary get a type with a private member and constructor, one factory returning `std::expected` or `std::optional`, and no implicit conversion back to the raw type; decoding goes through the same factory, and two kinds of id are two types. An id with no invariant to check can be `enum class JobId : std::uint64_t {}` (`JobId{n}` from a `std::uint64_t`, `std::to_underlying`).
- Dispatch statically by default: closed sets are `enum class` or `std::variant`; templates are constrained with a named concept, and the tests `static_assert` that the intended types satisfy it and a near miss does not. Virtual functions and type erasure are for open registries, stored callbacks and test seams, erased in one adapter that also converts JSON or bytes and catches what the conversion throws.
- Store callables in `std::move_only_function` (`std::function` rejects move-only captures), and reject an empty one where it is registered.
- In a `switch` over your own `enum class`, list every enumerator and omit `default`, so the compiler flags new ones (`-Wswitch`, part of `-Wall` in GCC); after the switch, fail in the project's error style, not with `std::unreachable()`, which is undefined behavior when reached. Turn wire or file integers into enums through a checking function, never a bare `static_cast`.
- Write one explicit-object member (`template <class Self> auto&& get(this Self&& self)`, returning `std::forward<Self>(self).member`; `decltype(auto)` would copy) instead of duplicated `const`/non-`const` overloads or CRTP. `Self` may be a derived type, whose member of the same name shadows yours, and on an rvalue the result refers into the temporary.
- A generic wrapper or container keeps `T`'s properties: `noexcept(std::is_nothrow_invocable_v<F&, Args...>)` or the matching `is_nothrow_*` trait instead of unconditional `noexcept` (a throw there is `std::terminate`); `requires`-constrained defaulted special members, so that trivial types stay trivially copyable and destructible; and code that also compiles for `void` results such as `std::expected<void, E>`. A container holds elements in raw storage through `std::construct_at` and `std::destroy_at`, never as an array of default-constructed `T` (C++26 has `std::inplace_vector`).
- Store or return a `std::string_view` or `std::span` only when a named owner outlives it and a comment says what invalidates it; a type that keeps a view of its argument rejects temporaries with a deleted rvalue overload (`Reader(const std::string&&) = delete;`, plus a `const char (&)[N]` overload so literals still bind; a `const char*` one would also accept `make().c_str()`). Don't return a range pipeline that refers to a local: move the container in, or materialize it with `std::ranges::to<C>(r)`. A coroutine takes by owning value (`std::string`, not `std::string_view` or `const&`) whatever it uses after its first suspension: a reference or view in the frame still points at the caller's object.
- Convert an integer that may not fit the target type only after `std::in_range<T>(v)` (which rejects `bool`, `char`, `wchar_t`, `charN_t` and enums), compare mixed signedness with `std::cmp_less` and friends, and reject fractional or out-of-range numbers from JSON instead of letting them truncate.
- A transform that usually changes nothing (redaction, escaping, normalization) pre-checks cheaply and reports "unchanged" without allocating: an empty `std::optional<std::string>`, or output into a caller's buffer.

## Errors

- A failure the caller routinely branches on is a `[[nodiscard]] std::expected<T, E>`; exceptions are for failures the immediate caller cannot handle. `E` is an `enum class` or small struct that says why the operation gave up (exhausted, deadline, cancelled, permanent) and carries what the caller acts on (path, key, code) plus the cause as a `std::error_code` or nested error, never flattened into a string.
- Convert exceptions from code you call (`nlohmann::json`, `std::filesystem` without the `std::error_code` overloads), and check stream state, at the boundary of an `expected`-returning API; neither may leak through it. Never use `try`/`catch` as control flow or to fall back silently to a default.

## Threads and lifetimes

- Threads are `std::jthread`s owned by an object that stops and joins them; never `detach()`. Declare the thread or pool after everything its body uses, so it joins first even if starting a later thread throws; lambdas that run on other threads capture by value, owning pointer or the `this` of a non-movable owner, never `[&]`.
- A stop request must wake waiting threads: wait with `std::condition_variable_any::wait(lock, token, pred)` and treat a `false` result as stopped. A plain `std::condition_variable` is not woken by `request_stop()`, so the `jthread` destructor can hang. A backoff or polling delay is such a wait, not `sleep_for`.
- An operation with a timeout computes one deadline from a steady clock (the injected one in tests) and passes it down; every nested wait and retry uses the remaining budget. Saturate the deadline, because for a huge timeout both `now() + timeout` and the conversion to the clock's duration can overflow.
- Queues between threads are bounded and say what full means (wait, drop and count, or fail); in a fan-out, one slow consumer must not stall the others and can see that it lost items. Guard "closed" and the queue with the same mutex, so nothing queued starts after a stop and a late submission is rejected, never lost.
- A callback may cancel or destroy its own registration: never join the thread you are running on, and keep a callable alive until its call returns.

## Resources and files

- Every OS handle (descriptor, `FILE*`, child process, mapping) is owned from the moment it exists by a move-only RAII type with no implicit conversion to the raw handle. Check file properties (type, size, owner) on the open handle (POSIX: `open` with `O_NONBLOCK`, then `fstat`, then clear the flag), not on a path checked before opening it.
- POSIX: a child process that does not need the terminal starts in its own process group (`POSIX_SPAWN_SETPGROUP`, or `setpgid` in both parent and child) and is owned by a guard that, on every path including exceptions, kills that group and only then reaps the child (afterwards the group id can be reused); every wait on it honors the deadline, even after its pipes close.
- POSIX: replace a state file atomically: `mkstemp` in the same directory (it creates the file with mode 0600, so `fchmod` it to the replaced file's mode), write, `fsync`, `rename`, then `fsync` the directory; remove the temporary on failure.
- Resolve configuration paths in a pure function of injected inputs (environment lookup, home directory) with a thin wrapper that reads the real environment.

## Untrusted input and wire formats

- Whatever outside input can grow has a stated limit, checked before allocating: lengths and counts (against the bytes remaining); line, record and file size; captured output (keep draining past the cap); nesting depth.
- For data that other versions of the program read or write: an unknown message type is skipped by its length and returned as unsupported; an unknown enumerator decodes to an explicit `unknown` with the raw value kept beside it; a missing optional field takes its default, while a missing required field is an error; unknown keys survive rewriting a file, and a file that does not parse is reported, never overwritten with defaults.

## Tests and tooling

- Time-dependent code takes its clock and wait function as parameters, so tests never sleep. Concurrency tests synchronize with promises or condition variables, never sleeps or polling, and every wait has a timeout (`wait_for`; `std::latch` has none) so a regression can fail instead of hanging.
- Only when asked to set up build, lint or CI policy: the project's standard (23 if unset) with `CMAKE_CXX_STANDARD_REQUIRED ON` and `CMAKE_CXX_EXTENSIONS OFF`; flags on targets, never directories, with warnings `PRIVATE`, warnings as errors only in CI and only on your own targets (the `COMPILE_WARNING_AS_ERROR` target property, not the global `CMAKE_COMPILE_WARNING_AS_ERROR`), and third-party includes `SYSTEM`; library hardening (libstdc++: `-D_GLIBCXX_ASSERTIONS`; libc++: `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST`); ASan+UBSan and TSan jobs with `-fno-sanitize-recover=all`; clang-tidy from a broad check set with a comment on each disabled check; a fuzz target for each decoder of untrusted input.
