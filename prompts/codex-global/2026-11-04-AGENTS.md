# Engineering preferences

- Before editing, understand the whole relevant flow, data ownership and existing architecture. Design the change from that view, not from where the symptom appears.
- Fix the underlying structure. Refactor decisively across the relevant boundary and consolidate duplication when that is simpler than a local patch; a small diff is not a goal. Delete code and tests the change makes obsolete.
- Adopt the best proven, well-maintained third-party library when it clearly beats hand-rolled code on performance, correctness or UI consistency and polish, and use it consistently across the relevant scope. Avoid speculative layers and unrelated rewrites. Preserve intended public behavior and contracts unless the request changes them.
- Keep tests minimal and deliberate: cover core capabilities and real failure, state and security boundaries. Do not test wording, trivial glue or implementation details, and do not add repetitive input matrices; merge or delete such tests when touching them.
- Verify with the narrowest relevant checks and user-level acceptance. Do not rerun a passed broad suite without relevant new changes or failures. Required CI still applies.
- Complete authorized work end to end. Ask only when a missing decision materially changes scope or correctness.
- Communicate concisely in the user's language: lead with the outcome, back claims with evidence, and state limits.

## Task orchestration

- Work directly by default. When a task runs linearly (no new requirements or design threads emerge midway, the user's messages do not branch it, and context has rarely been compacted), do not spawn subagents.
- Switch to new sessions once the task has diverged: the work or the conversation has branched, and the task is long, still changing and already compacted many times. Repeated compaction erodes decisions and detail, so organize the remaining work across one or more fresh sessions, or hand the unfinished part to a successor session.
- Give each new session a self-contained brief: goal, decisions and constraints still in force, current state with evidence, remaining steps and acceptance criteria. Split along independent threads, run sessions concurrently only when their edits do not conflict, and integrate and verify their results before reporting completion.
