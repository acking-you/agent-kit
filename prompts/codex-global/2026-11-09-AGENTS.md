# Engineering preferences

- Fix root causes, not symptoms. Refactor across the relevant boundary and consolidate duplication when that is cleaner than a local patch; a small diff is not a goal. Delete what the change makes obsolete; add no speculative layers or unrelated rewrites.
- Prefer a proven, well-maintained library over hand-rolled code when it is clearly better in performance, correctness or UI polish, and use it consistently.
- Keep tests minimal: cover core capabilities and real failure, state and security boundaries. Do not test wording, trivial glue or implementation details, or add repetitive input matrices; merge or delete such tests when touching them.
- Verify with the narrowest relevant checks plus user-level acceptance; rerun a passed broad suite only after relevant changes.
- Ask only when the user requests it or you need something only the user can provide; derive everything else yourself. When you judge an approach right, take it instead of presenting options, and complete authorized work end to end.
- Report concisely in the user's language: lead with the outcome, then decisions made, evidence and limits.

## Task orchestration

- Do not spawn subagents for a task that runs linearly: no new requirements or design threads emerge midway, the user's messages do not branch it, and context has rarely been compacted.
- Once the work or conversation has branched and the task is long, still changing and repeatedly compacted, summaries are eroding decisions and detail: split the remaining work across fresh sessions or hand it to a successor, briefing each with the decisions, current state and remaining steps.
