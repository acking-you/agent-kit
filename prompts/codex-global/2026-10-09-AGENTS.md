## TSearch Production SSH Login

- The `zellij` requirement applies only to SSH login, remote shell commands, and remote diagnostic sessions that need to remain attachable. Local macOS file inspection, source-code searches, edits, builds, and other non-SSH commands should run directly and must not be wrapped in `zellij` merely for persistence.
- All TSearch SSH login and remote shell commands must be run inside a persistent `zellij` session. Create or reuse the session before executing the login command, keep every login hop and subsequent inspection command inside that session, and leave it attachable when finished. Do not use a one-off bare SSH or transient shell session for these operations.
- When `/Users/boliu/tools/login.sh` is used for a TSearch environment, treat it as a two-stage login. The script opens the jump/host shell and copies the next login command to the macOS clipboard.
- To enter the real TSearch instance, use `login.sh --no-kitty <env-file>`. In this mode the clipboard contains the raw SSH command for the real instance; it is not merely a first-stage command.
- After the first-stage shell is ready, execute the clipboard command **inside that remote shell**, not in the local macOS shell. Do not infer the engine's process model from the first-stage host's process list.
- The default non-`--no-kitty` mode adds the `es/tsearch-engine/tool/kitty/login` helper and is the Kitty-specific path; do not mistake it for the required path to the real instance.
- Never print, log, or reproduce the clipboard command because it contains credentials. When automating the paste, suppress command echo while injecting it into the first-stage remote TTY.
- Preserve production safety after entering the instance: default to read-only inspection unless the user explicitly authorizes a mutation.

## Long-Running Task Continuation

- User preference (2026-09-23): for long waits such as large remote builds, create or update a recurring heartbeat on the current task to check progress, then yield the foreground turn. Do not spend a prolonged turn repeatedly sleeping or polling.
- Default to checking every 5 minutes unless the user specifies another interval or the task warrants a different cadence. Reuse an existing matching automation instead of duplicating it.
- Persist the running job/session identity, logs, current checkpoint, remaining steps, success criteria, and authorization boundaries before yielding. When the prerequisite finishes, automatically continue the already-authorized downstream work through validation and delivery; a successful build alone does not finish the task.
- Keep routine unchanged checks quiet. Notify on meaningful progress, failure, required user action, or final completion. Pause and verify the continuation automation once the entire requested task is complete. Preserve attachable remote sessions and do not modify unrelated automations.
